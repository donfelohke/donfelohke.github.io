01 / Thesis

Not a skin. An interaction system.

Glass Terminal is the shared design and interaction research connecting three different environments. Glass is a material vocabulary; terminal is a computing philosophy; XR is an optional spatial modality. They must remain separate architectural concerns that can work together through explicit interfaces.

01 · MATERIAL

Glass

Selective translucency, reflection, diffusion, depth and occlusion. Surface treatment must never become a substitute for hierarchy or contrast.

02 · COMPUTING

Terminal

Inspectable state, composable tools, keyboard precision, programmable behaviour, reproducible configuration and human control.

03 · SPACE

XR

Spatial references, anchors, volumes, embodied input and immersive presentation. XR extends the desktop; it does not replace the conventional workstation.

02 / Architecture

One philosophy. Separate layers.

WARENA owns the computing and graphics foundation. IKAI owns reflective experience and participant authority. GENJE owns creative movement and performance semantics. FELOH Corpus governs shared terms, evidence and provenance.

HUMAN INPUTKeyboard · pointer · touch · accessible switches · optional gaze · optional gesture · performer-authored movement
INTERACTION MODELFocus · selection · navigation · command execution · spatial manipulation · undo and recovery
2D / SPATIAL PRESENTATIONNative desktop windows · terminal panes · panels · scene objects · spatial composition
COMPUTING FOUNDATIONGNU/Linux · X11-first desktop policy · native graphics · OpenXR research · Guix / reproducibility

Boundary: OpenXR is an application/runtime interoperability API, not a desktop compositor or complete shell. Browser CSS glass is a web presentation technique, not physical optics and not the implementation architecture for WARENA or IKAI.

04 / Interaction

Multimodal, never gesture-only.

Each input method has a bounded responsibility. Users must retain equivalent, discoverable paths for essential tasks. XR interaction should be evaluated for comfort, precision, latency, accessibility and error recovery.

KEYBOARD / POINTER

Primary precision and command paths for desktop use. Keep focus visible and commands inspectable.

GAZE / HAND

Potential XR target-and-action pairing. Gaze does not silently execute destructive actions; hand input is not the only path.

VOICE / SWITCHES

Optional access paths for navigation and dictation, with explicit activation, privacy controls and alternatives.

BODY / MOVEMENT

Performer-authored movement and notation for GENJE. Capture, replay and sharing remain participant-controlled.

SPATIAL CONTEXT

Anchors and depth should communicate useful relationships, not add decorative complexity or cause visual fatigue.

REVERSIBILITY

Provide cancellation, undo, confirmation and recovery. Distinguish preview, selection and execution.

05 / Material system

Optics are not CSS.

A visual glass effect and a physical reflective display are different engineering problems. The web page uses CSS only to demonstrate one presentation language; IKAI's mirror track requires optical and hardware research.

INTERFACE MATERIAL

Frosted surface

Backdrop blur and translucent fills simulate diffusion in a rendered interface. They need opaque fallbacks and must not carry essential text without contrast validation.

PHYSICAL OPTICS

Two-way mirror

Partial reflection and transmission depend on illumination balance, coating, viewing geometry and display placement. This belongs to IKAI's optical validation track.

DISPLAY HARDWARE

Transparent OLED

Emissive transparent displays have different black-level, contrast, ambient-light and integration constraints. Do not treat them as interchangeable with mirrors.

06 / Roadmap

Build evidence in layers.

Start with a testable desktop design system and native interaction model. Do not make headset hardware, cameras, sensors or AI prerequisites for a useful workstation.

  1. Desktop design and usabilityDefine surface tokens, focus model, navigation, keyboard paths, contrast and responsive public-web expression.
  2. Native desktop feasibilityEvaluate X11-first composition, native graphics and Guile/Scheme integration without a web runtime dependency.
  3. Spatial interaction prototypeEvaluate OpenXR runtime availability, reference spaces, composition layers, input profiles and device compatibility.
  4. IKAI optical experimentValidate mirror/display geometry, luminance, viewing angles, privacy and participant-directed reflection.
  5. GENJE embodied experimentUse authored scores and synthetic movement first; measure timing, comfort, uncertainty and creative usefulness.
  6. Cross-project integrationTest shared contracts, data boundaries, recovery and reproducibility before considering a unified environment.

07 / Evaluation

Measure the experience.

Visual polish is not evidence of usability. Every prototype must state what was measured, under which conditions, with which hardware and which limitations.

READABILITY

Contrast on real surfaces, text scaling, transparency and foreground/background variation.

PERFORMANCE

Frame pacing, GPU cost, input latency, startup and idle resource use.

ACCESSIBILITY

Keyboard equivalence, focus visibility, target size, captions, switch access and reduced motion.

ERGONOMICS

Posture, eye strain, head movement, arm fatigue, session duration and recovery.

PRIVACY

Data minimisation, local processing, consent, capture indicators, retention and deletion.

REPRODUCIBILITY

Versioned configurations, repeatable builds, documented hardware and reproducible test conditions.

08 / Sources

Standards before spectacle.

The following primary sources establish technical boundaries and evaluation criteria. They do not validate a WARENA implementation or an IKAI/GENJE prototype.

  • Khronos OpenXR RegistryOpenXR 1.1 specifications, API references, extensions and conformance material.
  • OpenXR 1.1 specificationSpaces, composition, sessions and interaction profiles.
  • W3C WCAG 2.2Contrast, focus, input modalities, target size and reflow requirements.
  • MDN: backdrop-filterBrowser rendering behaviour and compatibility considerations.
  • MDN: prefers-reduced-transparencyUseful progressive enhancement; browser support is not universal.
  • Apple: Spatial layoutSpatial window and volume layout reference; platform-specific guidance.

Evidence rule: research documentation and a public design page do not establish implementation, user validation, hardware compatibility, deployment or product release. Those stages require separate artefacts and test evidence.
